# The audit of 2026-09-28: what was found, done and proposed

An audit of commit `a65e4aa` listed thirty-one items in six sections. Its
rules were: verify each item before acting, by reproducing it or reading the
code; change nothing that cannot be reproduced or that is disagreed with, and
say why; leave the items marked **[DESAIN]** as they are and propose instead;
and for every fix, a failing test first, then the change, then `npm run check`
green, then a commit that explains it. This page answers every item in that
order.

Each item has a verdict:

- **Confirmed** -- reproduced or read in the code, and fixed.
- **Partly confirmed** -- part of it held; what did not is said.
- **Not reproduced** -- the failure did not occur here; what was done instead
  is said.
- **Disagree** -- the item is not right as stated; nothing was changed for it.
- **Proposal** -- a feature or a design question. Nothing was built without the
  owner; the proposal is written out so the owner can decide.

The audit environment was Node 22.22.2 and PostgreSQL 16 with pgvector 0.6.0
on Ubuntu 24.04, which is the environment these checks ran in too.

## A. Tests and CI

### 1. The owner-mfa "enrol twice" test is flaky -- confirmed, fixed

It did not fail in the runs made here; the cause was found by reading it. The
test started the racing enrolment and attached its expectation
(`assert.rejects`) only after awaiting the other replica's commit. The refusal
arrives when that commit lands, on another connection, and can land first: for
a moment the rejection has no handler, and the test runner fails a test for
that. Widening the window by 100 ms reproduces
the failure every time. The expectation is now attached when the enrolment
starts. Commit `28df8c9`.

### 2. process.test "restart" fails depending on order -- confirmed, fixed

Not reproduced locally; it did fail on GitHub (CI run 172, `null !== 0`), and
the cause was found by reading. The deployment printed `console at` and only
then listened for SIGTERM, so a signal sent the moment it said it was ready --
as the test does, and as a supervisor may -- found nothing listening, and the
default action killed the process with the worker already claiming tasks and
handing nothing back. A synchronous sleep between the two lines reproduces it.
The listeners are now installed before anything starts; a signal during boot
is kept and stops the deployment once it has booted. A new test sends SIGTERM
while the deployment is still starting. Commit `28df8c9`.

### 3. `npm test` fails silently without `console/dist` -- confirmed, fixed

Three tests failed on their own terms, none saying the console was missing.
`pretest` now runs `scripts/require-console.ts`, which stops first and names
`npm run console:build`; `test/documents/require-console.test.ts` covers it.
Commit `28df8c9`.

### 4. No coverage in CI -- confirmed, done

CI runs the suite once with V8 coverage (`npm run test:coverage`).
`scripts/coverage-report.ts` writes the job summary: functions, branches and
lines, and the files with the most functions never called; it fails the job
when a file under `src/` is loaded by no test at all, and nothing else, because
a percentage threshold is a number people learn to write tests for rather than
a property. Child processes are started without `NODE_V8_COVERAGE`, so a test
that checks what a child inherits still sees exactly what it hands over.
Commit `28df8c9`; the first run on GitHub failed because a fresh checkout has
no `coverage/` directory for the report, fixed in `d424638` (CI run 174 green).
At `d424638`: 141 files loaded, functions 94.2%, branches 85.4%.

### 5. No Docker build, compose, health or smoke check in CI -- confirmed, done

A `docker` job builds the image from the Dockerfile, starts it with
`docker-compose.yml` beside a database on a fresh volume, waits for both to be
healthy, checks `/api/health`, runs `scripts/smoke.ts` inside the container,
checks that PID 1 is tini and that an orphaned process is reaped rather than
left a zombie (item 15), and stops the app with SIGTERM, requiring exit 0 and
the line saying it stopped on SIGTERM. Commit `28df8c9`.

The job had a race of its own, which CI run 176 found: the smoke check ran
inside the app's container, and the app's worker -- with no model, so no
runtime -- claimed the check's task first and halted it. The check now runs in
a container of the same image with the app stopped (`a53064f`), and the
docs say to run it that way anywhere.

## C. Agent CLI entries

Checked against the source of Hermes (`6e69a893`, v2026.9.24) and OpenClaw
(`da2bcd6`, v2026.9.6). Commit `4564c84`.

### 11. Hermes `chat --max-turns` and `--source` do not exist -- disagree, and a guard added

Both exist: Hermes declares them through a local alias of its argument
parser, which is why searching for the literal flag found nothing. Nothing was
changed for the claim. Reading the handler found something else: a value of 0
or less means no limit at all, so a spec's `maxTurns` must now be a whole
number of at least 1, and a malformed one is refused naming the entry.

### 12. OpenClaw `--isolated` / `--auth-env-only`, credential leak -- partly confirmed, fixed another way

The flags exist, but OpenClaw refuses both beside `--config`, which is how the
bridge reaches it, so they cannot be used. What they would have prevented was
checked directly: with a home of its own, every credential OpenClaw reads is
under `$HOME` except two model families, `amazon-bedrock/*` (AWS's default
credential chain -- on a cloud server, the instance's own role) and
`claude-cli/*` (the `claude` binary, which on a Mac reads the login keychain).
The entry now names them in `hostSignInModels`, and a role routed to one is
refused before anything starts, with a sentence saying why.

### 13. OpenClaw `--timeout 600` hardcoded -- confirmed, fixed

A task given two hours was ended by OpenClaw at ten minutes. A
`{wallClockSeconds}` placeholder now carries the run's own deadline (or the
lease), never 0, which OpenClaw reads as no limit. At its limit OpenClaw still
prints its result envelope, so the run is charged what it spent; a test covers
it.

### 14. Hermes reports no cost -- confirmed, fixed

Hermes' stream-json carries tokens and no price, and its `--usage-file` exists
only beside `-z`, which approves everything, so every Hermes run was charged
the deliberately high fallback rate. Hermes keeps each session's cost in its
own ledger; a spec's `costArgs` now reads it back after the run (`hermes
sessions export - --session-id <id>`, first line only): the provider's figure,
else Hermes' estimate, nought for a route a subscription covers, and unknown --
priced by the engine, not free -- for a price Hermes does not know.

## D. Deployment

### 15. PID 1 does not reap zombies -- confirmed, fixed

Node as PID 1 never waits for a process it did not start, and an agent CLI's
own children outlive it now and then. The image now runs tini as PID 1
(`ENTRYPOINT ["/usr/bin/tini", "--"]`), which reaps them and passes SIGTERM on.
The CI job of item 5 checks both. Commit `28df8c9`.

### 16. Linux only, because of `/proc` -- partly disagree, documents improved

"Linux only" was already stated, and the one `/proc` read has a fallback on
other systems, so it is untested elsewhere rather than impossible. The guide
now says how to run it on macOS or Windows (the container, with Docker
Desktop). Commit `9490f4b`.

### 17. The console is one large bundle -- confirmed, fixed

The sign-in page preloaded 446 KB of JavaScript gzipped, the charts alone
135 KB, though only two pages draw one. A company's pages and the deployment
settings now load when first opened; the chart styles come with the two pages
that draw charts; only what every page is built from is pinned into the vendor
chunk. The sign-in page now fetches 275 KB gzipped, and the charts arrive with
Overview. Checked in a browser: each page fetches its own chunk and none
reports an error. Commit `06c3e5b`.

## E. Missing features

### 18. No OpenTelemetry or Sentry -- proposal

What exists: every model call is a row in `llm_traces` with its cost, every
step is in the journal and the event log, and structured log lines go to
standard output. What is missing is export to an operator's own tools.

Proposed: an optional OTLP exporter, off unless `OTEL_EXPORTER_OTLP_ENDPOINT`
is set, emitting one span per task attempt with child spans per capability call
and model turn, carrying company, task and trace ids but never inputs or
outputs (they can hold customer data, and the redactor only knows the secrets
it was told about). Errors would be recorded on the span rather than sent to a
second service: an operator with Sentry points its OTLP intake at the same
endpoint. The cost is two small dependencies (`@opentelemetry/api` and the OTLP
HTTP exporter), which the repository rules require to be justified next to
them.

### 19. [DESAIN] Multi-user -- proposal only: a backup approver

One human owner is a deliberate principle of the specification, so nothing was
changed. The risk behind the item is real: if the owner is unreachable, tier 3
work waits indefinitely, and if the owner's devices are lost, recovery needs
operator access to the machine.

Proposed, without adding users: a **backup approver** -- a second person's
authenticator enrolled as a *restricted* factor that can only do two things:
approve or deny an item that has waited longer than a threshold the owner sets
(for example 48 hours), and freeze everything. It cannot loosen a control,
enrol or revoke a factor, change a budget, or see the console beyond the inbox.
Every use notifies the owner on every channel. This keeps "one owner decides
policy" while removing "one person's absence stops the company".

### 20. No OAuth connectors -- proposal

Today an integration is a token in the secret store, referenced by a vendor
file or an MCP entry; MCP servers that accept only OAuth (Notion, for one) are
named as such in `mcp-presets.ts` and cannot be connected. Proposed: an OAuth
2.1 authorization-code flow with PKCE in the owner API, for MCP servers first
(the MCP specification defines the discovery), storing the refresh token sealed
like any other secret and refreshing on use. It is a sizeable piece -- the
redirect, state, token refresh, revocation and the console screens -- and needs
real vendor accounts to verify, which this environment does not have.

### 21. No plugin system -- disagree with the framing, proposal

There is an extension system, and it is deliberately not code: a **bundle**
(signed, with a publisher the owner trusts) carries roles, skills, policies,
schedules and hooks as data; a **vendor file** adds a capability as a
declarative HTTP spec; an **MCP server** adds tools out of process; a
**runtime spec** adds an agent CLI. Code from a third party runs in its own
process, never inside the control plane that holds every company's secrets.
Proposed instead of an in-process plugin API: a documented bundle format page
and a `palugada bundle init` scaffold, so writing an extension is a first-hour
task rather than a reading exercise.

### 22. No git worktree per task -- proposal

`repo.read` and `repo.branch` are catalogue capabilities a deployment binds to
its remote with a vendor entry and a token; the `palugada-dev` bundle does its
work on a branch. What is missing is a local
checkout per task for a CLI runtime. Proposed: a workspace option on a runtime
entry that creates `git worktree add` under the run directory from a bare
mirror kept per repository, removes it when the run ends however it ends
(as the process tree already is), and never gives the run the push
credential -- the push stays a `repo.branch` capability call through the
broker, so a tier and an approval stay in front of it.

### 23. No WhatsApp, and Slack and Discord only send -- proposal

Telegram is the channel that can decide; Slack and Discord post through
incoming webhooks, which cannot carry buttons or be answered. Proposed, in
order of value for an Indonesian owner: WhatsApp through the Cloud API (Meta)
with message templates for approvals and interactive reply buttons, which needs
a verified business number and a webhook with its signature check; then Slack
as an app with interactivity, which is the same shape as Telegram's channel
(signed requests, buttons, a decision gated by tier). Both need real accounts
to verify and were not built blind.

### 24. Passkeys: the server verifies them, the console cannot use one -- confirmed, done

The audit was right, and it was worse than stated: there was no registration
ceremony either, so nothing could make a passkey, and the only one a
deployment ever held was one a test inserted. Now:

- `OwnerMfa.enrolPasskey` reads the browser's `attestationObject` (CBOR, with
  the key as a COSE key, read in `src/owner/passkey.ts` without a dependency)
  and checks the ceremony, the challenge, the origin, the relying party, that a
  person verified on the device, and the key (ES256, EdDSA, or RS256 of at
  least 2048 bits). Adding one needs a factor the owner already holds.
- The console signs in with a passkey, offers one in every confirm dialog when
  the owner has one, and adds one under Settings, Security. When a passkey
  cannot work -- plain HTTP, or the console opened at another address -- it
  says where it can.
- The relying party now defaults to the host of `PALUGADA_APP_URL_PUBLIC`;
  before, an unset `PALUGADA_RP_ID` meant `localhost` everywhere.

Tested with a software authenticator writing the real byte formats, every
refusal mutation-checked (36 of 36 killed), and watched working in Chromium
with a virtual authenticator, in English and Indonesian: a passkey made from
Security with a code, used to sign in, and used to revoke the code.

### 25. A vendor example per core capability -- partly done; the example had a defect

Reading the shipped example found that its one payment entry could never have
worked: it bound `invoice.issue` to Stripe with a JSON body and `amount_due`,
and Stripe's v1 API takes forms only, `amount_due` is computed rather than
accepted, and invoicing an amount takes two or three calls, which one entry
cannot make.

Twelve vendors were read from their own documentation, with no account and no
request made. Each candidate entry was held to the platform's two rules --
every write is read back, and every side effect carries a key the vendor
deduplicates by -- and half failed the second: GitHub branches, Hetzner,
Cloudflare record deletion, HubSpot notes, Vercel deployments and Xendit
invoices document no idempotency key at all. Those were left out rather than
shipped with a header the vendor ignores, and the guide now says which and
why. What was added, and what the platform needed to say it:

- `bodyEncoding: "form"`, for Stripe, Twilio, Mailgun and every API that
  takes a form (commit `b0c6132`);
- `{credentialBasic}`, a key sent as an HTTP Basic user name, or a
  `user:password` pair, encoded by the platform and redacted like the key
  (`b0c6132`);
- an idempotency key in the body, as the vendor's own unique id for what is
  made, judged by building the body rather than trusting a flag (`bf9fc0d`);
- `describe.moneyUnits`, an amount in whole units described in cents, so a
  policy threshold compares the same money (`bf9fc0d`);
- the example now binds `invoice.issue` (Midtrans QRIS, below),
  `social.publish` (Mastodon) and `metrics.read` (Plausible) beside the
  existing Resend and Cloudflare entries (`bf9fc0d`). `npm run smoke` binds all
  six.

"Per core capability" is not met, and cannot honestly be met from here: the
remaining capabilities either have no vendor with an idempotency key, need
OAuth (item 20), or need several calls. None of the six has been run against
the vendor itself; that needs the owner's accounts.

### 26. Midtrans, Xendit, QRIS -- partly done

Midtrans is bound: `invoice.issue` in the example is a QRIS payment through
Midtrans' Core API (`POST /v2/charge`, `payment_type: qris`), authenticated
with the server key as Basic, the amount in whole rupiah, the `order_id` the
platform's idempotency key -- Midtrans documents an `order_id` as usable once
and answers a reused one with 406, so a retry after a lost answer charges
nobody twice -- and read back from
`/v2/{order_id}/status` (pending or settled). It points at Midtrans' sandbox,
so a copied example charges nobody. The answer carries the QR code's address
for the agent to hand on.

Xendit is not bound. Its invoice API carries no idempotency key and does not
refuse a repeated `external_id`, so a retry could bill twice; Xendit also
calls it legacy in favour of Payment Sessions, which have no key either.
Xendit's own QRIS through `/v3/payment_requests` is the candidate once its
documentation shows a key. Midtrans' Snap (the hosted checkout) was not used:
its status endpoint answers "not found" until the customer picks a payment
method, so a write could not be read back.

### 27. No LICENSE and no release -- proposal; the owner chooses

A licence is the owner's decision and was not chosen here. The README already
says the code is visible but not licensed for reuse. The choice, briefly:

- **AGPL-3.0** keeps anyone who runs a modified PALUGADA as a service obliged
  to publish their changes; the usual choice for a control plane someone might
  host for others.
- **Apache-2.0** allows anything, including closed hosted versions, with a
  patent grant; the usual choice when adoption matters more than reciprocity.
- **A source-available licence** (FSL, BSL) keeps commercial hosting to the
  owner for a period and then becomes open.

Once chosen: a `LICENSE` file, the `license` field in both `package.json`
files, the README section, and a first tagged release (`v0.1.0`) with a
changelog generated from the commit subjects since the repository began.

### 28. [DESAIN] Companies cannot be deleted -- proposal only

Deliberate: the event log is append-only, and a company is frozen, exported or
retained. Nothing was changed. The real need behind the item is erasure --
a customer's personal data, or a company the owner wants gone. Proposed:
**closing** a company, which freezes it, exports it for the owner, and then
purges its rows by the retention machinery that already exists, leaving in the
event log only a tombstone (the company id, when it was closed, by which
factor, and the export's hash). The log stays append-only; the data does not
stay.

### 29. [DESAIN] The role eval is structural -- proposal only

Deliberate, and explained in `src/eval/role-eval.ts`: scoring a change to a
role by replaying its reference runs against a live model would cost money and
give a different answer each time, and F17.3 wants a score before the owner
decides. So the score checks that the capabilities the reference runs used
survive the change, that the grants they depended on are still held, and that
each negative case's failure stays prevented. The audit asked for this to be
written in the README's limits. That is documentation rather than a change to
the design, but the rules say to propose for **[DESAIN]** items, so the
sentence is proposed here, ready to add:

> **A role's eval score is structural.** A change to a charter, skills or model
> routing is scored against its reference runs by what they needed -- the
> capabilities, the grants, the failures that must stay prevented -- not by
> running them again, so it cannot tell a better answer from a worse one.

## F. Optional ideas

### 30. A demo to show -- proposal

A `npm run demo` that starts PALUGADA against the scripted model the
end-to-end test already uses, with the standard company, a week of history
generated by running it rather than by inserting rows, and a TOTP secret
printed once -- so the console can be shown without a model key. The same
state can be recorded as a short screen capture for the README.

### 31. A lighter way to install -- proposal

Today there are two: the container (`docker compose up`) and running it
directly with PostgreSQL and pgvector installed. Proposed: a compose file that
needs no hand-written `.env`, with `npm run setup` run in a one-shot container
on first start to write the secrets and print the authenticator's QR code, so
the whole install is `git clone` and `docker compose up`. A SQLite build is not
proposed: row-level security in PostgreSQL is what isolates the companies.
